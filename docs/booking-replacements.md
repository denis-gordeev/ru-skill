# Booking replacements

Этот документ фиксирует исследование по замене legacy-навыков `srt-booking` и `ktx-booking` на российский сценарий.

Статус исследования: 2026-04-29.

## Что уже подтверждено

- Официальный пользовательский поток у РЖД существует, но он завязан на полноценный checkout, пользовательский аккаунт и платёжный сценарий.
- `tutu.ru` и Яндекс Путешествия дают сильный пользовательский сценарий поиска и покупки ЖД-билетов, но в открытых материалах не подтверждён свободный публичный API для стабильной агентной автоматизации покупки.
- Уже реализованный `yandex-rasp` закрывает значимую read-only часть задачи: станции, расписания и поиск маршрутов без логина и без brittle browser automation.

## Decision matrix

| Кандидат | Тип поверхности | Официальность | Что можно подтвердить публично | Основные ограничения | Решение |
| --- | --- | --- | --- | --- | --- |
| `rzd-booking` | Официальный web/app checkout | Да | У РЖД есть официальный пользовательский поток покупки билетов | Нужны аккаунт, платёжный flow и устойчивость к изменениям checkout-поверхности; свободный публичный API для агентного бронирования не подтверждён | Не брать в автоматизированный MVP |
| `tutu-ru` | Агрегаторный web checkout | Нет | Есть сильный пользовательский сценарий поиска, выбора мест и покупки | Публичный read-only веб-поток есть, но свободный public API для booking automation не подтверждён | Рассматривать только как read-only/handoff-кандидат |
| `yandex-travel-trains` | Агрегаторный web checkout | Нет | Есть пользовательский сценарий поиска и покупки ЖД-билетов | Партнёрский API Яндекса документирован для travel inventory, но не как свободный public train-booking API для локального skill | Рассматривать только как read-only/handoff-кандидат |
| `yandex-rasp` + handoff | Публичный API + внешний переход | Частично | Стабильный read-only API уже внедрён в репозиторий | Не покрывает выбор мест, оплату и post-booking lifecycle | Текущий базовый путь для target-линейки |

## Вывод по milestone

- Полноценную автоматизацию покупки российских ЖД-билетов нельзя считать хорошим следующим target-навыком, пока не появится официальный и устойчивый программный интерфейс без антибот-обходов.
- Ближайший реалистичный вариант для миграции - не новый write-skill, а аккуратный read-only/handoff слой поверх уже существующего `yandex-rasp` или поверх стабильных train-search страниц агрегаторов.
- Legacy `srt-booking` и `ktx-booking` сохраняются ради совместимости, но не должны становиться шаблоном для новых российских интеграций.

## Итог на 2026-04-29

- Отдельный railway handoff-skill не открывается.
- `yandex-rasp` уже покрывает стабильный read-only baseline: станции, расписания, маршруты и ориентиры по цене без логина и без checkout automation.
- Самостоятельный handoff-пакет сейчас дал бы только thin-wrapper над внешними пользовательскими checkout-поверхностями РЖД, `tutu.ru` или Яндекс Путешествий, но не новую устойчивую API-функцию внутри репозитория.
- Поэтому replacement для `srt-booking` и `ktx-booking` фиксируется как `yandex-rasp` для discovery + ручной переход пользователя во внешний checkout, без открытия нового `target`-пакета.

## Критерий закрытия Milestone 5

Milestone 5 считается закрытым, если выполнено одно из двух условий:

1. Подтверждён официальный и устойчивый российский booking-source без логина, закрытых API и brittle anti-bot обходов, после чего можно делать новый target-package.
2. Зафиксировано, что такого source нет, а репозиторий официально ограничивает replacement для railway-booking уровнем `read-only discovery + external handoff`, не расширяя write-автоматизацию оплаты и бронирования.

Во втором случае backlog закрывается документно и регрессионно, без попытки искусственно дотянуть legacy-booking до новой продуктовой линии.

На 2026-04-29 Milestone 5 закрыт вторым способом.
